✅ **游戏本体文件（可执行文件 + 数据文件 + 自带 DLL）100% 未被修改。**

所有修复均采用「**目录内代理 DLL + 独立配置文件**」方式，属外挂式覆盖，
**不触碰、不替换、不修改任何游戏原始文件。**

| # | 新增文件 | 性质 | 必需 |
|---|---|---|---|

## 二、为什么这不算修改游戏

Windows 的 DLL 加载顺序是：

```
程序自己的目录  →  系统目录  →  PATH
```

游戏（`gcii.exe`）调用 `d3d9.dll` 时，Windows **优先加载游戏目录里的同名 DLL**。
所以：

```
没有 DXVK：  gcii.exe → C:\Windows\SysWOW64\d3d9.dll    （微软原版，太老，Win11 黑屏）
有 DXVK：    gcii.exe → .\d3d9.dll  ← DXVK 现代实现 → Vulkan  → 你的显卡
```

**游戏本体完全不知道自己被"接管"了** ——
它仍然调用同样的 `Direct3DCreate9()` API，
只是背后的实现从微软的旧 DLL 换成了 DXVK。

**没有打补丁、没有 hex 编辑、没有修改任何二进制。**

这就是为什么：

- ✅ 游戏本体不需要改一个字节
- ✅ 删掉这几个新文件，游戏立刻回到原始状态
- ✅ Steam「验证游戏文件完整性」不会报错（因为本体文件哈希没变）

## 三、如何为你的电脑生成专属审计报告

你自己跑一遍下面的方法，就能得到一份**属于你的**审计报告，
里面有你自己机器的真实路径、时间戳、MD5 —— 比任何模板都有说服力。

### 方法 1：时间戳分离法（最直观）

**原理**：游戏本体文件的修改时间全部等于 **Steam 安装时刻**，
而你的修复操作必然发生在**安装之后**。两组时间完全分离 = 本体未被触碰。

```bash
cd "/path/to/Ground Control II"

# 列出所有文件及修改时间，按时序排列
find . -type f -printf "%T+  %p\n" | sort
```

**看什么**：

| 现象 | 含义 |
|---|---|
| 绝大多数文件时间戳**完全相同** | 它们是 Steam 一次性安装写入的 → 未被改动 |
| 只有 3 个文件（`d3d9.dll` / `dxgi.dll` / `dxvk.conf`）时间明显更晚 | 这些是你新增的 |
| 有少数文件时间较晚，但文件名是 `gcii_d3d9.log` / `profiles/*` | 这些是**游戏/DXVK 自己运行生成的**，不是你改的 |

> Windows 用户可以用 PowerShell 等价命令：
> ```powershell
> Get-ChildItem -Recurse -File | Sort-Object LastWriteTime |
>   Select-Object LastWriteTime, Length, FullName | Format-Table -AutoSize
> ```

### 方法 2：MD5 指纹法（可提交给审核者）

**原理**：记录游戏本体文件的 MD5，与官方发布版本对比（或与其他用户的机器对比）。
哈希一致 = 字节级未被修改。

```bash
cd "/path/to/Ground Control II"

# Windows / Git Bash
md5sum gcii.exe binkw32.dll mss32.dll *.sdf

# macOS / Linux
md5 gcii.exe binkw32.dll mss32.dll *.sdf
```

> PowerShell 等价命令：
> ```powershell
> Get-FileHash gcii.exe, binkw32.dll, mss32.dll -Algorithm MD5 |
>   Format-Table Hash, Path -AutoSize
> ```

**把你的结果填进这张表**（下面这是空模板）：

| 文件 | 大小 (bytes) | MD5 | mtime |
|---|---|---|---|
| `gcii.exe` | | | |
| `binkw32.dll` | | | |
| `mss32.dll` | | | |
| `gc2data.sdf` | | | |
| `gc2movies.sdf` | | | |

### 方法 3：Steam 官方校验（最权威，推荐）

这是**最省事也最有说服力**的一条：

1. Steam 库 → 右键「Ground Control II」→ **属性**
2. 「已安装文件」→ 点击「**验证游戏文件的完整性**」
3. 结果应为：**所有文件校验通过**

Steam 会把本地文件与官方服务器上的原始哈希逐一比对。
**全部通过 = 官方级别的证明：你的游戏文件与官方原版完全一致。**

> 💡 **建议把这一步的结果截图**，放进 GitHub README 或 Steam 帖子。
> 这比任何文字说明都管用。

### 方法 4：删除测试（反证法）

删除 `d3d9.dll` / `dxgi.dll` / `dxvk.conf` 三个文件后，
游戏会立刻回到**原始的"黑屏卡死"状态** ——

证明：**整个修复效果完全来自这几个新增文件，而不是对游戏本体的改动。**
如果本体被改过，删掉新增文件后症状不会恢复原样。

> 测完记得把这 3 个文件放回去。

### 方法 5：文件列表对比法（最严格）

如果你想要最强的证据，在**安装修复之前**做一次快照：

```bash
# 修复前
cd "/path/to/Ground Control II"
find . -type f -printf "%T+ %s %p\n" | sort > ~/before.txt

# ... 安装 DXVK 修复 ...

# 修复后
find . -type f -printf "%T+ %s %p\n" | sort > ~/after.txt

# 对比
diff ~/before.txt ~/after.txt
```

**预期输出**：只有 3 行新增，没有任何删除或修改。

> 如果你已经装完了修复也没关系 —— 用方法 3（Steam 校验）能拿到同样的结论。

## 四、已验证的工作状态

| 项目 | 状态 |
|---|---|
| 黑屏卡死 | ✅ 已解决（DXVK 接管） |
| 竖条花屏 | ✅ 已解决（`forceRefreshRate` 匹配刷新率） |
| 画面缩一块 | ✅ 已解决（稳定配置下不出现） |
| 鼠标不能动 | ✅ 已解决（`enablePresentTiming = False`） |
| 启动弹窗 | ⚠️ 无害，需手动点「否」（见下） |
| 游戏内分辨率选项只有 5 项 | ⚠️ 未解决（游戏引擎限制，见下） |

### 已知限制 1：游戏内分辨率只有 5 项

游戏只读取分辨率列表的**去重后前 5 项**，
而系统的分辨率枚举顺序是**按宽度升序**排列：

```
[0] 640x480  [1] 720x480  [2] 720x576  [3] 800x600  [4] 1024x768
...（高分辨率排在很后面，永远取不到）
```

**这是游戏自身的代码限制，与 DXVK 配置无关。**
理论上可用 `forceAspectRatio` 过滤把列表压到 5 项（使目标分辨率落入前 5），
但那需要配合 `DXVK_FORCE_WINDOWED` 环境变量，
**在从 Steam 直接启动的场景下无法生效**，故未采用。

### 已知限制 2：启动时的硬件检测弹窗

游戏启动时读注册表里的旧格式硬件信息，DXVK 不写这些老项，
游戏误判"显存 0MB / 无 DX9 驱动"而报警。

**完全不影响运行**，点「否 / No / Cancel」正常进入。
干净关掉它需要改游戏本体或改系统配置，都违背本方案原则，故不处理。

## 五、给读者 / 审核者的建议验证流程

如果你是**下载别人发布的修复包**，想确认安全，按这个顺序做：

| 步骤 | 操作 | 预期 |
|---|---|---|
| 1 | 核对包内文件 | 应该**只有** `dxvk.conf` 和说明文档，**没有任何 DLL / EXE** |
| 2 | 检查 DLL 来源 | 自己从 DXVK 官方 releases 下载，不从任何第三方包获取 |
| 3 | 装完后跑 Steam 校验 | 全部通过 |
| 4 | 检查游戏目录新增文件 | 只有你刚放的 3 个 |
| 5 | 需要还原 | 删掉那 3 个文件即可 |

**一个好的修复包，永远不应该包含游戏本体文件或第三方二进制。**
如果某个包里有 `gcii.exe` 或来路不明的 DLL，**不要用**。
